# Architecture

The browser calls a single-origin FastAPI service. SQLite stores the task, routing decision, provider ID, activity and result. Submission returns 202. A background call to Grok produces a validated route; no side-effecting call runs on an invalid response. A single process owns the polling loop, reading pending Devin and video jobs independent of browser selection. On restart uncertain launches and report reviews are not automatically replayed.

Repository tasks launch at most one Devin session. The original request and Grok plan are scoped to the selected repository and optional publication permission. For opted-in jobs, Grok reads a bounded structured report after Devin finishes. No follow-up write is triggered by its output. Media needs a separate atomic confirmation. Provider endpoints are fixed and each receives only its own server-side key; provider text is never evaluated.

GitHub browsing previews file text and re-reads only the approved paths at the pinned SHA for Grok. Devin receives repo, ref, SHA and the original request (with secrets redacted), separate from Grok's advisory plan, not the GitHub token or file bundle. Actual branch/file telemetry comes from a GitHub PR in the selected repo; in-session activity comes from Devin's messages and status detail, not inferred commands or live file handles.

The separate session workspace resolves the task base or GitHub PR head once per tree load. Each permitted tree entry has a process-local signature binding the job to its repository, commit, path, and blob. File tabs read that immutable blob without fetching a new branch tip or following symlinks. The read-only workspace does not send its opened files to either agent. Refresh the tree after restarting the server to obtain fresh signatures.

The marketplace reads public Skills.sh metadata without provider credentials. A browser cookie identifies its library and allows one editable review per skill; these are local community reviews, not verified identities. Untrusted catalog metadata and reviews are displayed as text and never read by agents. A submission snapshots explicitly selected, installed skills. They supplement routing and implementation without changing the goal, granting permissions or triggering a separate session. Optional report review uses the request and Devin's report, not skill instructions.

Workspace-only entries pin a GitHub commit and do not dispatch agents. Drafts live in the browser tab. Publishing requires server authentication and snapshot signatures for every edit. It uses either the current GitHub App user token for an installed repository or a dedicated write PAT with a server allowlist when OAuth is not configured. The write path creates a tree and a commit, then creates a new ref; it never updates an existing ref.

GitHub App OAuth uses one-time state bound to a browser cookie and PKCE. In the default server mode the immutable GitHub account ID must match the configured owner before the browser can access the cabinet or APIs. The login screen, its assets and OAuth entry routes are public. Demo entry works only in demo mode and never creates a GitHub connection. User tokens are held in memory per browser connection and never put into job records, agent prompts or background polling. The Setup URL ignores the untrusted installation ID; repository entitlement comes from GitHub's authenticated user installation list. The GitHub App is not a replacement for Devin's own repository authorization.

An implementation can have one approved image and one approved video on the same task. SQLite records each phase; a video generation can continue polling after restart, but uncertain launches are not replayed. The bridge saves bounded, validated media locally and uploads it via the Devin organization attachment API before starting one implementation session.
